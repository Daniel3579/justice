# ОПИСАНИЕ ВАРИАНТОВ ИСПОЛЬЗОВАНИЯ СИСТЕМЫ «Генеративная система формирования исковых заявлений»

## 1 Общие сведения

Настоящий документ содержит описание вариантов использования автоматизированной системы «Генеративная система формирования исковых заявлений» (JUSTICE). Варианты использования отражают взаимодействие пользователя с системой и обработку основных и альтернативных сценариев в рамках текущей версии.

## 2 Участники и внешние системы

| Участник / система | Назначение |
| --- | --- |
| Пользователь | Вводит описание ситуации, уточняет сведения, задает вопросы, просматривает и экспортирует результат. |
| Frontend JUSTICE | Предоставляет веб-интерфейс чата, страниц входа и профиля, отображает результаты и выполняет клиентские операции. |
| Backend JUSTICE | Принимает HTTP-запросы, управляет авторизацией и чатами, запускает генерацию, обработку диалога и экспорт DOCX. |
| Ollama / языковая модель | Используется для извлечения фактов, классификации намерения, составления частей иска и ответов на вопросы. |
| ChromaDB | Предоставляет локальный поиск по подготовленной базе правовых документов. |
| DDGS | Обеспечивает веб-поиск правовой информации. |
| PostgreSQL | Хранит пользователей, сессии и историю чатов в серверном режиме. |

## 3 Общие правила выполнения сценариев

- Основной интерфейс взаимодействия пользователя с системой — чат.
- Для генерации и обработки сообщений backend принимает текст длиной не более 8000 символов; пустые сообщения отклоняются.
- Классификация сообщения определяет одно из намерений: новое дело (`new_case`), дополнение существующего дела (`update`) или вопрос (`question`).
- При создании нового дела выполняется извлечение фактов, поиск правовой информации, составление текста иска и рендеринг по шаблону.
- При дополнении дела исходная фабула объединяется с дополнением пользователя, после чего генерация выполняется повторно.
- При вопросе система формирует ответ с учетом доступных фактов, текста иска, локальных правовых материалов и последних реплик диалога.
- Регистрация, вход, профиль и серверная история чатов используют backend-авторизацию и PostgreSQL. При этом frontend по умолчанию может работать в mock-режиме, если `VITE_MOCK_AUTH` не установлена в строку `false`.
- В текущем backend endpoint'ы `/me` и `/chats` защищены Bearer-токеном. Endpoint'ы `/generate`, `/chat` и `/export/docx` в представленном коде не требуют авторизации.

## 4 Варианты использования

Каждый вариант использования содержит назначение, участников, предусловия, инициирующее событие, основной поток, альтернативные потоки и результат выполнения.

| Поле | Значение |
| --- | --- |
| Идентификатор | UC-01 |
| Наименование | Регистрация пользователя |
| Цель | Создать учетную запись пользователя в системе. |

| Предусловия | Пользователь находится на странице входа/регистрации. Backend доступен. Для серверной регистрации frontend должен работать с `VITE_MOCK_AUTH=false`. |

| Основной поток | 1. Система принимает email и пароль.<br>2. Backend нормализует email и проверяет его формат.<br>3. Backend проверяет минимальную длину пароля.<br>4. Система проверяет, существует ли аккаунт с указанной почтой.<br>5. При успешной проверке создается пользователь и сессия.<br>6. В mock-режиме учетная запись создается на стороне frontend и не является серверной регистрацией. |
| Результат | Создана учетная запись и активная сессия; пользователь получает доступ к функциям системы в пределах своей авторизации. |

| Наименование | Создание искового заявления |

| Предусловия | Открыт интерфейс чата. Backend и Ollama запущены. Для локального поиска подготовлена ChromaDB; доступность веб-поиска зависит от DDGS. |

| Основной поток | 1. Frontend передает сообщение в `POST /chat` либо исходный текст в `POST /generate`.<br>2. Backend проверяет, что сообщение не пустое и не превышает 8000 символов.<br>3. Модуль обработки диалога определяет намерение как `new_case`.<br>4. Модель извлекает факты и формирует структурированную карточку `CaseFacts`.<br>5. Система выполняет локальный поиск правовой информации в ChromaDB и веб-поиск через DDGS.<br>6. Модель формирует фактическую и правовую части на основе извлеченных фактов и найденных материалов.<br>7. Модуль render формирует контекст и подставляет данные в шаблон `app/templates/isk.j2`.<br>8. Система возвращает текст иска, факты, недостающие сведения и список источников.<br>9. Frontend отображает результат пользователю. |
| Альтернативные потоки | A1. Если сообщение пустое или превышает лимит, backend возвращает HTTP 400.<br>A2. Если намерение не распознано, применяется резервная логика классификации: при отсутствии дела запрос обычно рассматривается как новое дело.<br>A3. Если локальный поиск недоступен, его результаты не включаются; генерация может продолжиться с доступными веб-результатами.<br>A4. Если веб-поиск не дал результатов, система продолжает работу без веб-источников.<br>A5. При ошибке генерации backend возвращает HTTP 500 с полем `error`; результат не считается успешно сформированным.<br>A6. Если сведений недостаточно, система отмечает недостающие данные, а не должна подменять их вымышленными значениями. |
| Результат | Сформирован черновой проект искового заявления и возвращены структурированные факты, недостающие сведения и источники.<br>Документ требует проверки пользователем. |

## 5 Ограничения и допущения

- Mock-режим авторизации является демонстрационным и не обеспечивает серверное хранение учетных записей и истории чатов.
- Автоматический детерминированный валидатор юридической актуальности норм и корректности сформированного иска отсутствует.
- Расчет неустойки реализован только для поддерживаемых типов нарушения и зависит от полноты и корректности исходных сумм и дат.
- Доступность генерации зависит от работы Ollama и доступности необходимых моделей; локальный поиск зависит от подготовленной ChromaDB, веб-поиск — от DDGS.
- Наличие результата генерации не означает его готовность к подаче в суд без дополнительной проверки.
